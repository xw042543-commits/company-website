# 用户注册与登录系统设计

**日期：**2026-09-24
**状态：**已审核，待实施

## 目标与范围

本阶段将现有的登录、注册和忘记密码预览页面接入真实后端，建立普通用户账号体系。第一版包含注册、联系方式验证、登录、退出、忘记密码和基础“我的账号”。暂不包含收藏、咨询历史、员工账号、内部审批和权限后台。

注册时用户填写姓名、邮箱或手机号、密码，并同意用户协议和隐私政策。邮箱与手机号都可用于登录，但注册时只需提供其中一种。邮箱账号通过邮件链接验证，手机账号通过短信验证码验证。

## 方案选择

采用 Spring Security、PostgreSQL 服务端 Session 和 HttpOnly Cookie。PostgreSQL 保存用户、验证凭证、密码重置凭证和 Session，后端使用 Spring Security 进行身份验证和请求授权。浏览器只保存不可由 JavaScript 读取的 Session Cookie，不在 `localStorage` 或 `sessionStorage` 保存密码、JWT 或其他长期登录凭证。

这一方案与当前单体架构一致，也遵守项目“Redis 仅用于缓存”的约定。相比 JWT，服务端 Session 可在退出、修改密码和注销账号后立即失效，不需额外的刷新令牌轮换和撤销名单。本阶段不接入 Auth0、Supabase 等第三方身份平台，避免在正式账号和合规资料未齐时增加外部依赖。

## 系统结构

请求流程保持为：Next.js 页面调用 Spring Boot `/api/v1` REST 接口，Spring Security 识别和验证 Session Cookie，服务层执行账号规则，JPA Repository 访问 PostgreSQL。

后端在独立的 `auth` 模块中组织账号、验证、密码重置和 Session 配置，不把身份逻辑混入院校、搜索、文章或咨询模块。第一版只定义 `USER` 角色；将来员工系统使用独立设计，不提前把员工权限塞进本次实现。

邮件和短信通过统一的通知接口调用。开发和测试环境使用可控的本地实现，便于获取测试链接或验证码；生产环境只允许使用真实服务商实现。没有配置正式服务商时，生产注册必须保持关闭。

## 数据模型

### `user_accounts`

保存用户的内部 `id`、姓名、规范化邮箱、规范化手机号、密码摘要、账号状态、邮箱验证状态、手机验证状态、用户协议版本、隐私政策版本及创建、更新和软删除时间。

邮箱和手机号可空，但至少必须有一项；已填写的值必须唯一。账号状态只允许 `PENDING_VERIFICATION`、`ACTIVE`、`DISABLED` 和 `DELETED`。用户注销采用软删除，公开接口不再返回账号信息，同时立即撤销所有 Session。具体保留期在正式隐私政策确定后再配置。

### `user_verification_tokens`

保存联系方式验证记录，包含用户、验证类型、凭证摘要、失效时间、尝试次数、已使用时间和创建时间。数据库不保存验证码或验证链接中的明文密钥。新凭证生成后，同用户、同用途的旧凭证失效。

### `password_reset_tokens`

保存密码重置凭证摘要、用户、失效时间、已使用时间和创建时间。每个凭证只能使用一次；密码重置成功后，同用户的其他未使用凭证和全部 Session 一并失效。

### Session 表

使用 Spring Session JDBC 提供的服务端 Session 表，由 Flyway 纳入项目迁移，不依赖运行时自动建表。普通登录有效期为 24 小时，选择“记住我”后为 30 天。后端在登录成功时重新生成 Session ID，防止 Session 固定攻击。

## REST 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/v1/auth/register` | 创建待验证账号并触发邮件或短信 |
| `POST` | `/api/v1/auth/verify-email` | 验证邮箱链接凭证 |
| `POST` | `/api/v1/auth/verify-phone` | 验证手机短信码 |
| `POST` | `/api/v1/auth/resend-verification` | 重新发送验证信息 |
| `POST` | `/api/v1/auth/login` | 使用邮箱或手机号登录 |
| `POST` | `/api/v1/auth/logout` | 销毁当前 Session |
| `GET` | `/api/v1/auth/session` | 返回当前登录状态和最小用户信息 |
| `GET` | `/api/v1/auth/csrf` | 获取浏览器后续写请求使用的 CSRF Token |
| `POST` | `/api/v1/auth/forgot-password` | 申请密码重置 |
| `POST` | `/api/v1/auth/reset-password` | 使用邮件凭证或短信码重置密码 |
| `GET` | `/api/v1/account` | 查看当前账号基本资料 |
| `PUT` | `/api/v1/account/password` | 验证原密码后修改密码 |
| `DELETE` | `/api/v1/account` | 二次确认后软删除账号 |

所有写请求使用 JSON 且限制请求体大小。不含敏感信息的成功响应使用明确 DTO，不直接序列化 JPA 实体。错误沿用现有 `ApiErrorResponse` 和 `X-Trace-Id`。

注册和忘记密码类接口对账号是否存在使用统一的对外提示，避免被用于批量探测用户。登录失败统一返回“账号或密码错误”；未完成联系方式验证的账号不允许登录，但可重新申请验证信息。

## 身份验证与安全

密码使用 Spring Security 提供的自适应密码编码器，数据库只保存摘要。具体强度参数在实施阶段根据 Java 21 和生产资源测试确定，不使用 MD5、SHA-1 或无盐快速哈希保存密码。

Cookie 设置 `HttpOnly` 和 `SameSite=Lax`，生产环境必须设置 `Secure`，并只通过 HTTPS 传输。对会改变服务器状态的浏览器请求启用 CSRF 防护；Next.js 先获取可提交的 CSRF Token，再在后续请求中携带。CORS 仅允许配置中的官网来源并允许 Cookie，不使用通配来源。

登录失败、注册、重发验证信息和密码重置都按客户地址及帐号标识进行限制。具体阈值通过类型安全的应用配置提供。实施时从现有咨询防滥用功能中复用或抽取客户地址信任规则，不复制第二套代理识别逻辑。日志可记录 `traceId`、结果和不可逆标识，但不记录密码、验证码、重置凭证、Cookie 或 Session ID。

## 前端交互

现有 `/{locale}/login`、注册和忘记密码页面保留当前视觉结构，改为真实表单和后端请求。前端对请求中传递 Cookie，通过 `/api/v1/auth/session` 确定是否登录，不以本地变量或页面文案伪造登录状态。

注册后进入“请完成验证”状态；验证成功后由用户显式登录，不通过验证链接自动创建长期 Session。账号页面第一版只显示基本资料、修改密码、退出和注销账号入口。注销需明确告知影响并二次确认。

页面结构和固定按钮保持中英双语，错误信息根据当前 `locale` 展示。前端不把后端原始异常、数据库信息或服务商错误直接显示给用户。

## 错误处理

- 请求字段、页面参数或业务校验不合法：`400`。
- 未登录或 Session 已失效：`401`。
- 已登录但不允许执行当前操作：`403`。
- 对外可查找资源不存在：`404`。
- 邮箱或手机号等唯一数据冲突：`409`，但涉及账号枚举的端点使用统一对外响应。
- 请求频率超限：`429`。
- 邮件、短信、Session 存储或必要依赖暂时不可用：`503`。

未预期异常继续由全局异常处理器转换为通用 `500` 错误，响应不含堆栈、SQL、用户敏感数据或第三方密钥。

## 配置与上线开关

注册使用显式的类型安全配置开关。开发和测试环境可使用本地通知实现开启完整流程；生产环境默认关闭注册。只有以下条件全部满足时才能开启：

1. 老板已确认用户协议正式文本和版本号。
2. 老板已确认隐私政策正式文本和版本号。
3. 邮件与短信服务商配置、发件身份、短信签名及模板已完成验收。
4. 正式域名 HTTPS、Cookie 安全属性和 CORS 来源已完成验收。
5. 用户确认生产环境可正式开放注册。

配置不足时应“关闭优先”，不自动退回到本地验证码、固定验证码或不验证模式。

## 测试与验收

- Flyway 迁移可在空库和现有数据库上执行，不破坏院校、搜索、文章和咨询数据。
- 数据库拒绝无联系方式账号、重复规范化邮箱或手机号、非法状态和不完整的协议记录。
- 注册、邮箱验证、手机验证、重发验证信息和重复账号均有服务及 HTTP 集成测试。
- 邮箱和手机号都能登录；错误密码、未验证、已禁用和已注销账号无法登录。
- 普通登录和“记住我”使用不同的 Session 有效期，登录时 Session ID 会更换。
- 退出、修改密码、重置密码和注销账号后，相关 Session 立即失效。
- 验证凭证和密码重置凭证过期、重复使用、猜测超限和并发使用均会被拒绝。
- CSRF、CORS、Cookie 属性、请求体限制、限流、日志脱敏和统一错误响应都有覆盖。
- 本地通知实现仅在开发和测试配置中可用，生产配置缺失时启动失败或保持注册关闭。
- 前端登录、注册、验证、忘记密码和账号页面覆盖成功、等待、错误、过期和服务暂时不可用状态。
- 后端全量测试、前端单元测试、类型检查、Lint 和构建必须全部通过。

## 实施顺序

1. 新增数据库迁移、账号实体与数据约束。
2. 接入 Spring Security、Spring Session JDBC、Cookie、CORS 和 CSRF 基础配置。
3. 实现注册、邮箱/手机验证及可替换通知接口。
4. 实现登录、退出、Session 状态和 Session 撤销。
5. 实现忘记密码、重置密码和修改密码。
6. 实现基础账号资料和账号注销。
7. 将现有前端预览页面接入真实 API。
8. 完成全量验证、安全审核和中文 API/配置文档。

## 不包含

本阶段不实现 OAuth/微信/谷歌登录、多因素认证、收藏、咨询历史、员工权限、内部审批、管理员后台、组织/租户、自助更换邮箱或手机号，也不接入正式邮件或短信服务商。这些功能如需实现，应另行确认业务规则、数据权限和合规边界。
